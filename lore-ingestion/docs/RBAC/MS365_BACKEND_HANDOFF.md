# MS365 (Outlook + Teams) ACL — Backend Handoff

**Status:** Implementation complete — pending real Microsoft Graph validation (credentials not yet available).  
**Audience:** lore-engine engineers wiring MS365 query-time access control.  
**Produced by:** LOR-64 (fetch) + LOR-65 (discovery).

---

## 1. Overview

### LOR-64 — Outlook Connector

LOR-64 built the raw fetch layer for Microsoft 365 in `infra/outlook/`:

- `fetcher.py` — Azure AD client credentials auth, `graph_get()` with pagination and 429/5xx retry, `DeltaStore` per-mailbox/per-channel delta tokens
- `normalizer.py` — Raw Graph API dict → `KnowledgeEvent` (same schema as Gmail)
- `run.py` — CLI: `--stage fetch` pulls Outlook mail and Teams messages, writes JSONL to `output/raw/`

LOR-64 produces **event data** — the messages themselves.

### LOR-65 — MS365 Identity Discovery

LOR-65 built the discovery layer in `infra/outlook/discovery.py`:

- `discover_users()` — enumerates all enabled, non-guest users from `GET /users`
- `discover_teams_channel_members()` — maps every Teams channel to its member Azure AD object IDs via a three-level Graph traversal (groups → channels → members)
- `emit_ms365_identities()` — writes the identity artifact
- `emit_teams_scope_map()` — writes the Teams ACL scope map

LOR-65 produces **ACL data** — who can see what.

The two sets of artifacts are complementary: LOR-64 generates the knowledge graph content; LOR-65 generates the access control data that gates visibility in Neo4j.

### How to run discovery

```powershell
# Requires AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET in .env
python -m infra.outlook.run --org ezobooks --stage discover
```

Writes both artifacts under `output/outlook/`.

## 2. Identity Artifact

**File:** `output/outlook/{org}_ms365_identities.json`

This file enumerates every enabled, non-guest user in the Microsoft 365 tenant. It is the MS365 equivalent of the Gmail person registry — the authoritative list of people the pipeline knows about.

### Schema

```json
{
  "org": "ezobooks",
  "source": "ms365",
  "count": 42,
  "identities": [
    {
      "objectId":     "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
      "displayName":  "Alice Smith",
      "upn":          "alice.smith@ezobooks.in",
      "email":        "alice.smith@ezobooks.in",
      "account_type": "member"
    },
    {
      "objectId":     "ffffffff-gggg-hhhh-iiii-jjjjjjjjjjjj",
      "displayName":  "Bob Patel",
      "upn":          "bob.patel@ezobooks.in",
      "email":        "bob.patel@ezobooks.in",
      "account_type": "member"
    }
  ]
}
```

### Field reference

| Field | Type | Description |
|-------|------|-------------|
| `objectId` | string (GUID) | Azure AD object ID — immutable, globally unique across all Microsoft services. This is the primary key for identity resolution. |
| `displayName` | string | Full name as shown in Teams / Outlook. |
| `upn` | string | User Principal Name — login format `user@domain.com`. Usually matches email. |
| `email` | string | `mail` field from Graph API. Falls back to `upn` when a mailbox has not been assigned (common for synced accounts). |
| `account_type` | string | Always `"member"`. Guests are excluded at discovery time. |

The list is sorted deterministically by `objectId`. `count` is the length of `identities`.

## 3. Teams Scope Artifact

**File:** `output/outlook/{org}_ms365_teams_scopes.json`

This file maps every MS365 user (by `objectId`) to the list of Teams channel scope IDs they are a member of. It is the MS365 equivalent of `{org}_user_scopes.json` from the Slack pipeline.

### Schema

```json
{
  "org": "ezobooks",
  "source": "ms_teams",
  "person_count": 38,
  "scopes": {
    "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee": [
      "ms365:channel:19:abc123@thread.tacv2",
      "ms365:channel:19:def456@thread.tacv2"
    ],
    "ffffffff-gggg-hhhh-iiii-jjjjjjjjjjjj": [
      "ms365:channel:19:abc123@thread.tacv2"
    ]
  }
}
```

### Field reference

| Field | Type | Description |
|-------|------|-------------|
| `org` | string | Organization slug. |
| `source` | string | Always `"ms_teams"`. |
| `person_count` | int | Number of users with at least one channel membership. |
| `scopes` | object | `objectId → [scope_id, ...]`. Keys sorted by objectId; scope lists sorted alphabetically. |

A user who belongs to N channels will have N entries in their scope list. A user who belongs to no channels will be absent from the `scopes` dict entirely (not present with an empty list).

---

## 4. Scope Format

MS365 Teams channel scope IDs use the format:

```
ms365:channel:{channelId}
```

**Examples:**
```
ms365:channel:19:abc123def456@thread.tacv2
ms365:channel:19:general-channel-id@thread.tacv2
```

**Generated by:** `ms365_channel_scope(channel_id)` in `common/scopes.py`.

**Predicate:** `is_ms365_channel(scope_id)` returns `True` for any string starting with `ms365:channel:`.

### Why `ms365:channel:` and not `teams:channel:`

LOR-64 introduced `teams_channel(team_id, channel_id)` → `"teams:channel:{team_id}:{channel_id}"` as a utility function for the fetch path. That format embeds both IDs and was written to Neo4j — it is a persisted, breaking-change format that must not be removed.

LOR-65 introduces `ms365_channel_scope(channel_id)` → `"ms365:channel:{channel_id}"` as the **authoritative ACL scope format**. Graph API channel IDs are globally unique, so the `team_id` prefix is redundant for ACL purposes. The `ms365:` namespace makes it unambiguous that this scope came from the MS365 discovery pipeline.

**For ACL enforcement, always use `ms365:channel:` scope IDs** (from the Teams scope artifact). The `teams:channel:` format exists for internal fetch-path bookkeeping only.

## 5. Backend Consumption

### Load at startup

```python
import json
from pathlib import Path

org = "ezobooks"

# Load identity artifact
identities_path = Path(f"output/outlook/{org}_ms365_identities.json")
id_data = json.loads(identities_path.read_text(encoding="utf-8"))
# Build lookup: objectId → identity record
object_id_to_identity = {u["objectId"]: u for u in id_data["identities"]}

# Load Teams scope artifact
scopes_path = Path(f"output/outlook/{org}_ms365_teams_scopes.json")
scopes_data = json.loads(scopes_path.read_text(encoding="utf-8"))
# Direct lookup: objectId → [scope_ids]
object_id_to_scopes = scopes_data["scopes"]
```

### Build permissions for a logged-in user

```python
def get_ms365_scope_ids(azure_object_id: str) -> list[str]:
    """Return the Teams channel scope IDs for a user.

    Returns [] if the user is unknown or has no channel memberships.
    Fail-closed: an unknown user sees nothing.
    """
    return object_id_to_scopes.get(azure_object_id, [])
```

### Pass scope_ids to the Neo4j query

```python
user_scopes = get_ms365_scope_ids(azure_object_id)

cypher = """
CALL db.index.vector.queryNodes('knowledge_embeddings', $k, $embedding) YIELD node AS n, score
WHERE n.scope_ids IS NOT NULL
  AND size(n.scope_ids) > 0
  AND any(s IN n.scope_ids WHERE s IN $userScopes)
  AND NOT coalesce(n.deleted, false)
RETURN n, score
ORDER BY score DESC
LIMIT $k
"""

results = session.run(cypher,
    embedding=query_embedding,
    k=20,
    userScopes=user_scopes,
)
```

### Discovery → ACL flow

```
--stage discover
  │
  ├── discover_users()
  │     GET /users → enabled member users
  │     → output/outlook/{org}_ms365_identities.json
  │
  └── discover_teams_channel_members()
        GET /groups (Teams-provisioned)
          → GET /teams/{id}/channels
              → GET /teams/{id}/channels/{id}/members
        Invert: objectId → [ms365:channel:{id}, ...]
        → output/outlook/{org}_ms365_teams_scopes.json

Backend at startup:
  load identities → load scopes → build objectId → permissions lookup
  → wire to Neo4j query gate
```

### When to re-run discovery

| Event | Action |
|-------|--------|
| New employee joins | Re-run `--stage discover`. Until then the new user gets `[]` → sees nothing (safe, fail-closed). |
| New Teams channel created | Re-run `--stage discover`. |
| User added/removed from a private channel | Re-run `--stage discover`. Stale artifact means the user retains or loses access until refresh. |
| Full re-ingestion | `--stage discover` runs as part of the standard pipeline — nothing extra needed. |

## 6. Relationship to LOR-64

| Artifact | Produced by | Purpose |
|----------|-------------|---------|
| `output/raw/{org}_outlook_mail_*.jsonl` | LOR-64 `--stage fetch` | Raw Outlook mail messages for the pipeline |
| `output/raw/{org}_ms_teams_*.jsonl` | LOR-64 `--stage fetch` | Raw Teams messages for the pipeline |
| `output/outlook/{org}_ms365_identities.json` | LOR-65 `--stage discover` | Who exists in the tenant |
| `output/outlook/{org}_ms365_teams_scopes.json` | LOR-65 `--stage discover` | Who can see which Teams channel |

LOR-64 and LOR-65 are independent stages — neither depends on the other at runtime. The typical ingestion order is:

```
python -m infra.outlook.run --org ezobooks --stage discover   # LOR-65 ACL data
python -m infra.outlook.run --org ezobooks --stage fetch      # LOR-64 event data
```

Running discovery before fetch ensures ACL artifacts are available before knowledge nodes are written to Neo4j.

## 8. Production Readiness

When valid Azure credentials are supplied in `.env`, both commands execute immediately without any code changes:

```powershell
# Discovery — enumerate users + Teams channel members, write ACL artifacts
python -m infra.outlook.run --org ezobooks --stage discover

# Fetch — pull Outlook mail + Teams messages, write JSONL
python -m infra.outlook.run --org ezobooks --stage fetch
```

LOR-64 and LOR-65 are designed to operate against real Microsoft Graph APIs once credentials become available. The full pipeline covered:

| Step | Component |
|------|-----------|
| Credential validation | `validate_for("outlook_discovery")` / `validate_for("outlook_fetch")` |
| Azure AD authentication | `get_access_token(settings)` — client credentials flow, in-memory cache, auto-refresh |
| User enumeration | `discover_users()` — `GET /users`, guest/disabled exclusion |
| Teams channel membership | `discover_teams_channel_members()` — groups → channels → members |
| Identity artifact | `emit_ms365_identities()` → `output/outlook/{org}_ms365_identities.json` |
| Teams scope artifact | `emit_teams_scope_map()` → `output/outlook/{org}_ms365_teams_scopes.json` |
| Outlook mail fetch | `fetch_mail_for_user()` — delta sync per mailbox |
| Teams message fetch | `fetch_channel_messages()` — delta sync per channel, replies attached |
| Delta token persistence | `DeltaStore` — atomic write via `common.checkpoint` |
| JSONL output | `output/raw/{org}_outlook_mail_*.jsonl`, `output/raw/{org}_ms_teams_*.jsonl` |
| Normalization | `normalizer.py` — raw Graph dict → `KnowledgeEvent` |

No future code changes are required for production operation once Azure credentials are available.
