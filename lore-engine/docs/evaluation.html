Lore GraphRAG Evaluation

Does an ontology-typed knowledge graph retrieve better than plain vector RAG over a company's email, and where does it fail? Lore was built with a real client, EZO Books, on their real email and code history. This page is the evidence, criterion by criterion.

1 · Research question and experimental alignment

One question, three falsifiable hypotheses

ProblemCompany decisions live in email threads. People ask "why was X decided" or "what did Y decide about Z", and the answer's text often does not name the person or decision asked about.
ObjectiveRetrieve the exact facts, decisions and tasks that answer such questions, with sources, for one real company.
MethodLLM-extracted typed knowledge graph (7 node types, typed edges) plus graph-expansion retrieval, compared with vector RAG on the same embeddings.
ExperimentTwo test sets that separate relation questions (where the graph should help) from single-email lookups (where it should not).
HypothesisPredictionTested byOutcome
H1 The graph helps when the answer is connected by an edge, not by shared wordsLore beats vector RAG on relation questions55 graph questions, node recall@10supported

H3 The graph costs latencyLore is several times slowermedian latency, both testssupported

Test A · 55 graph questionsGenerated from the graph by three templates: tasks assigned to a person (15), why a decision was made (20), what a person decided on a topic (20). Ground truth is the Cypher result for that pattern, so neither system grades itself.
Test B · 60 single-email lookupsAn LLM wrote one question from one email each; ground truth is that email's thread. A control: the graph should not help here.

Golden evaluation set: the fixed baseline

Before any system ran, both test sets were built once and frozen as versioned files. Every number on this page (both baselines, the main run and all four ablation cells) is scored against these same 115 questions and the same answer labels, so a change in score comes from the system, not from the questions.

Golden fileQuestionsLabelled answersHow each label was fixed
graph_questions.json (Test A)55268 nodesThe Cypher traversal for the question's pattern, stored with the question. Tasks of a person: 144 answers, 3 to 18 per question. Why decided: 24, 1 to 3 per question. Person on topic: 100, 3 to 13 per question
questions.json (Test B)6060 threadsThe email thread the question was written from, using the raw email rather than the graph, so extraction errors count against Lore
  • Ambiguity removed: a person named in a question must have a unique name in the graph, and answers to the two person families must span at least two threads.
  • Answerable only: answers are limited to nodes the engine is allowed to serve, and lookup threads need at least 500 characters and three extracted facts.
  • Rebuildable: fixed seeds (7 for Test A, 42 for Test B) regenerate the identical set from the same graph (make_graph_questions.py, make_dataset.py).

Interpretation

  • Why the graph wins Test A. Only 4% of the correct task texts contain any part of the person's name, so text similarity cannot find them; the graph reaches them through the ASSIGNED_TO edge. "Why" questions find the right thread either way, but Lore returns the justifying Fact almost twice as often (0.65 against 0.35) by following BECAUSE edges.
  • Why it loses Test B. In a single-email lookup the question and the answer share wording, which is exactly what embeddings match. The ablation locates the cost in the LLM query analysis (−0.23). Our reading, not yet tested directly, is that it steers retrieval towards people and relations, so the source email drops out of the top 10. With the keyword fallback Lore reaches 0.63, still below vector RAG at 0.75.
  • Where we do not claim a result. The "why decided" gain has an interval touching zero, so it is a trend on 20 questions, not a finding.
  • Latency. About 8 s median for Lore against 0.35 s for vector search: query analysis, expansion, rerank and an LLM call.

What the ablation shows. The LLM query analysis is the trade-off at the heart of the system: it is what makes "what did this person decide about this topic" answerable (+0.32), and it is also what costs single-email lookups (−0.23). The reranker repairs part of that cost (+0.27 on lookups) and helps "tasks of a person". No single configuration wins both tests, so the next step is to route by question type: lookup-style questions to the keyword and vector path, relationship questions through the analysis and graph path.

5 · Limitations and failure analysis

What does not work, and why we think so

FailureEvidenceFailure point (Barnett et al.)Cause
Single-email lookupshit@10 0.40 against 0.75 for vector RAGMissed top-ranked documentsMeasured: LLM query analysis costs −0.23; the reranker recovers +0.27. Fix proposed: route lookups away from the analysis path
"Tasks of a person"node recall 0.10; 18 correct tasks for one person, only 10 slotsNot in contextHypothesis, not yet tested: person hubs have hundreds of edges and the beam keeps 30
Recency and code questions"most recent change" cannot be answeredMissing contentThe code index has no usable commit dates

Threats to validity

  • Ground truth comes from the same LLM-extracted graph, so an extraction error counts as truth, and the templates favour the structure the graph encodes.
  • One organisation; 15 to 20 questions per family, so several intervals are wide.
  • Retrieval is measured, answer quality is not: there is no human-judged answer score.
  • The client's data is private, so questions are regenerated from the graph rather than published.
