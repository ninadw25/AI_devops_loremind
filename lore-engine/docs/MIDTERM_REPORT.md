# Does an ontology-typed knowledge graph beat plain vector RAG over company email?
CSE 4011 — Project Phase 2 (mid-term). System: Lore (`lore-ingestion` builds the graph, `lore-engine` answers over it).

## 1. Research question and hypotheses
**RQ.** On questions whose answer is defined by *relationships* (who was assigned what, why a decision was made, what a person decided about a topic), does retrieval over an ontology-typed knowledge graph beat standard vector RAG?
- **H1** The graph helps where the answer text does not contain the entity asked about (relation lives on an edge).
- **H2** The graph does not help on single-hop lookups (literature predicts this, §6).
- **H3** The graph costs latency.

## 2. System and ontology
LLM extraction (schema-guided) turns each email thread into typed nodes and edges. Ontology: **7 node types** (Person, Organization, Topic spine; Decision, Task, Fact, Event content) and **9 predicates** (DECIDED, BECAUSE, ASSIGNED_TO, REGARDING, SUBJECT_OF, STATED_BY, MENTIONS, PARTICIPATED_IN, WORKS_AT). The engine uses it at query time: person/topic entity anchors, then a beam expansion whose edge weights come from per-edge priors and per-intent boosts (`domain/retrieval/frontier.py`), then cross-encoder rerank.
Graph (EZO Books, live counts in `results/summary.md`): 11,584 threads → 27,063 knowledge nodes, 13,562 persons, 3,609 topics, 85,392 relationships.

## 3. Method
Three systems, same embedding model (`nvidia/nemotron-3-embed-1b`), top-10 results:
1. **raw_rag** — LangChain + FAISS over raw email threads (what a normal pipeline indexes).
2. **node_rag** — LangChain + FAISS over the extracted nodes (same text as the graph, no structure).
3. **lore** — graph retrieval.

**Questions (55, deterministic).** Three templates, one per ontology pattern; ground truth is the Cypher result for that pattern (stored with each question), not an LLM judgement: `person_tasks` (Task→ASSIGNED_TO→Person, n=15), `decision_why` (Decision→BECAUSE→Fact, n=20), `person_topic` (Person→DECIDED→Decision→REGARDING→Topic, n=20). Named people are unique in the graph. Seeds fixed; regenerate with `make_graph_questions`.
**Metrics.** node recall@10 = matched ground-truth nodes / min(|GT|,10); thread recall@10 likewise over distinct threads; median latency; paired bootstrap 95% CI (5,000 resamples).
A first, separate test (60 LLM-written single-thread lookups, `run_eval.py`): Hit@10 baseline 75% vs Lore 63%, 0.4 s vs 5.4 s.

## 4. Results (`results/summary.md`, regenerated by `report.py`)
| | person_tasks | decision_why | person_topic | ALL |
|---|---|---|---|---|
| raw_rag thread recall | 0.06 | 0.82 | 0.04 | 0.33 |
| node_rag node recall | 0.03 | 0.35 | 0.01 | 0.14 |
| **lore node recall** | **0.20** | **0.70** | 0.01 | **0.31** |
| Lore − node_rag, 95% CI | +0.17 [+0.09,+0.26] | +0.35 [+0.10,+0.60] | 0.00 | +0.17 [+0.08,+0.27] |
Latency (median): vector baselines ≈0.3 s, Lore ≈7 s (includes LLM analysis and rerank).

## 5. Interpretation and evidence
- **H1 supported.** For `person_tasks`, **4%** (6/144) of correct task texts contain any token of the person's name, and for `person_topic` **1%** (1/100). The name is only on the edge, so text embedding cannot match it; the graph can. Lore recovers 6.7× more correct tasks than node-level vector search.
- **`decision_why`.** Thread recall is 0.82 for all systems (the decision text in the question finds the thread) but Lore finds the *justifying Fact node* twice as often (0.70 vs 0.35) by following BECAUSE.
- **H2 supported** by the first test (single-thread lookup: baseline better).
- **H3 supported**, ≈20× latency.
- **Not supported: `person_topic`.** All systems ≈0.

## 6. Failure analysis
Observed for `person_topic`: the person was anchored, the frontier expanded from a hub with 978 neighbours but kept 30, and the final cross-encoder rerank scores text similarity only (ignores graph provenance), so the Person∩Topic intersection is lost. The LLM entity-analysis step also has an 800 ms timeout and logs `analysis_timeout`. These are hypotheses from logs, not yet fixed or ablated. Matches Barnett et al.'s "missed top-ranked documents / not in context" failure points.
**Limitations.** One organisation; templated questions test the three patterns the ontology encodes (the graph was built from those predicates, so this favours it — it tests *whether the structure is usable*, not general QA); small n per family; ground truth is only as good as the LLM extraction (a wrong edge is "correct" ground truth); no answer-quality/faithfulness metric yet; node matching uses a 40-character text prefix; LLM-written first test has vague questions (several threads could answer), so recall there is a lower bound.

## 7. Literature (verified)
- Lewis et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*, 2020, arXiv:2005.11401.
- Edge et al., *From Local to Global: A Graph RAG Approach to Query-Focused Summarization*, 2024, arXiv:2404.16130 — entity graph + communities; beats vector RAG on global sensemaking.
- Peng et al., *Graph Retrieval-Augmented Generation: A Survey*, 2024, arXiv:2408.08921.
- Gutiérrez et al., *HippoRAG*, NeurIPS 2024, arXiv:2405.14831 — KG + Personalized PageRank for multi-hop retrieval.
- Han et al., *RAG vs. GraphRAG: A Systematic Evaluation and Key Insights*, 2025, arXiv:2502.11371 — RAG wins single-hop detail, GraphRAG wins multi-hop (our H1/H2).
- *When to use Graphs in RAG* (GraphRAG-Bench), arXiv:2506.05690 — graphs often underperform vanilla RAG; gains depend on question type.
- *Ontology Learning and Knowledge Graph Construction: A Comparison of Approaches and Their Impact on RAG Performance*, arXiv:2511.05991 — ontology-guided KGs outperform vector baselines (closest to our design).
- *OMD-GraphRAG: Ontology-Guided Extraction…*, arXiv:2603.25152.
- Barnett et al., *Seven Failure Points When Engineering a RAG System*, 2024, arXiv:2401.05856.

## 8. Reproduce
```
python -m benchmarks.rag_eval.make_graph_questions
python -m benchmarks.rag_eval.build_raw_index --events <gmail_filtered.jsonl>
python -m benchmarks.rag_eval.run_graph_eval --systems raw_rag node_rag lore   # engine on :8000
python -m benchmarks.rag_eval.report
python tools/gen_tests.py domain/context.py domain/sources.py domain/retrieval/person.py domain/scoring.py
```
Requires the Neo4j graph (private customer data), `NVIDIA_API_KEY`, and the engine running.
